# Process algebra programme self reflection mandate

Applies to work on the process-algebra, formal-proof, fossilized-state, generated-view and associated migration programme in this workspace. It does not replace unrelated repository policies. Follow the human user's current instructions when they refine this scope.

Read `research/self-reflection-mandate-20261013/MANDATE.md` when working in this programme. At each meaningful design, implementation, assurance or migration checkpoint:

- State the intended claim and exact scope, identify the evidence actually obtained, and distinguish declarations, executable checks, model proofs, implementation proofs and accepted admissions.
- Examine the claim's strongest relevant counterexample or falsifier, unresolved assumptions, interpretation seams and authority boundaries. Do not invent a fault to perform criticism; retaining a decision is valid when justified.
- Ask whether custom code or duplicated meanings can collapse into the common grammar. Report additional surface area honestly; a reusable prototype is not a demonstrated production reduction.
- Preserve corrections and their predecessors. Record material reflection in an additive migration note or a new checkpoint record with source/evidence links. A short completion report should include material uncertainty and the resulting decision.
- Do not turn reflection into authorization, a new goal, a recurring task or an unbounded review loop. Propose further work only within the user's scope. Pending reflection must prevent an unsupported assurance claim, not halt unrelated authorised work.

For this migration stage, leave existing application source and prior research artifacts unchanged unless the user explicitly authorizes otherwise. Document additions before transfer. Reflection records are evidence-linked decision summaries, not claims to reveal private reasoning or to constitute formal proof.
